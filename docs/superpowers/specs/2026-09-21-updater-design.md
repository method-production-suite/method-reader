# Design: how the Tauri app updates itself

Date: 2026-09-21 · Status: accepted. The open decision below (losing
install-time codesign pinning) was accepted and recorded in
`docs/retired-coverage.md`. The judgement half landed 2026-09-21; the
transport half is [its own plan](../plans/2026-09-21-updater-transport.md),
on branch `worktree-updater-transport`; the window half is the
interface-pass session's, against the contract sent the same day.
Decision it serves: [ADR 2026-09-21](../../adr/2026-09-21-doors-not-commands.md),
which says v0.6.1 waits for this.
Piece A of [the parity plan](../plans/2026-09-21-parity.md).
Evidence: [the parity audit](https://github.com/method-production-suite/method-reader/blob/7eb40e5/docs/parity-audit.md).

## The question

The Tauri app cannot update itself. Until it can, v0.6.1 must not take the
bundle identifier, because moving a user onto an app with no updater is a
one-way door.

The plan named two candidates and said the tension between them was the
real content of this spec. It is, and measuring turned up a third that is
better than either.

## What was measured, not assumed

All of this is from Tauri's own documentation and this repository, on
2026-09-21.

**The plugin is not a dependency yet.** `desktop/src-tauri/Cargo.toml` has
`tauri-plugin-shell` and `tauri-plugin-dialog`. No updater.

**Signing is mandatory and cannot be disabled.** The plugin needs a key
pair generated by `tauri signer generate`. The private key becomes a CI
secret; the public key goes in `tauri.conf.json`. Tauri's own words about
the private key: *"if you lose this key you will NOT be able to publish
new updates to the users that have the app already installed."*

**The macOS update artifact is a `.tar.gz` of the `.app`**, plus a `.sig`,
produced when `bundle.createUpdaterArtifacts` is true. It is NOT the DMG.
This matters more than it looks: the handover depends on there being
exactly one `.dmg` on a release, and a `.tar.gz` is not a `.dmg`, so the
two rules do not collide.

**The endpoint can be a static `latest.json`** on the GitHub release,
listing a url and signature per `OS-ARCH` key. TLS enforced.

**`download()` and `install()` are separate calls.** The API says
"Download the updater package. Call install later to install it." So
there IS a gap between fetching and swapping.

**But the downloaded path is not exposed to JavaScript.** The `Update`
object carries `version`, `currentVersion`, `body`, `date` and `rawJson`,
and the download is an internal resource addressed by an `rid`. So the
gap exists and cannot be used from the frontend to inspect the bytes.
This is the single most important measurement in this document and it
constrains everything below.

**The webview has no build step.** `tauri.conf.json` says
`frontendDist: "../ui"` and every import in `desktop/ui/` is a relative
`./` ES module. The window cannot import TypeScript from `src/`.

**But there is already a pattern for getting engine logic into the
window.** `desktop/ui/notes.js` is GENERATED from a markdown file by
`tools/build-desktop-notes.ts`, and `tests/desktop-notes.test.ts` asserts
the committed module is exactly what the generator produces. That is a
solved problem in this repo, not a new one.

## The two behaviours at risk

Everything else about the updater is replaceable. These two are not
obviously so, and both come from `docs/retired-coverage.md`'s insistence
that the pinning and the downgrade defence "have to survive whatever
shape" the updater takes.

### 1. Codesign requirement pinning

`UpdateInstall.swift` verifies the downloaded DMG and the app inside it
against a designated requirement: Apple's anchor, the Developer ID
intermediate, a Developer ID Application leaf, team `XSRB3D643J`, and the
bundle identifier. An attacker needs this project's Apple certificate.

Tauri's updater verifies its own minisign signature instead. **The chain
of trust becomes one private key**, and Apple's certificate is not
consulted at install time. If that key leaks, a signed malicious update
installs.

This is a real reduction in the strength of the guarantee, and it is the
thing to decide knowingly rather than discover.

Two mitigations exist and neither is free:

- **Notarization still applies to the artifact itself.** The `.app`
  inside the tarball is Developer ID signed and notarized by the release
  pipeline, so a swapped-in bundle is a notarized bundle. What is missing
  is the *check at install time* that it is OURS specifically.
- **The download/install gap cannot be used**, because the path is not
  exposed to JS. Verifying between them would mean Rust, which means a
  command, which the ADR just refused.

### 2. The git-describe downgrade defence

This is the one "found the hard way", and it is subtler than a version
comparison.

`UpdateCheck.isNewer` treats a pre-release suffix that looks like git
describe output (`0.6.0-1-g965cb10`, `-dirty`) as a build **at or past**
the tag, so the tag is never offered as an update to it. Its own comment:

> treating it as a pre-release would install a downgrade on every
> post-tag dev build

Semver disagrees: by semver, `0.6.0-1-g965cb10` is LESS than `0.6.0`, so
a plain semver comparator offers 0.6.0 as an upgrade to a build that is
already past it. **Tauri's updater uses semver.** So this defence is lost
by default, and the symptom is a downgrade loop on developer machines
rather than anything a user sees.

The classic trap the same function guards against, string ordering
putting `0.10.0` before `0.9.0`, is handled correctly by semver and is
not at risk.

## Three options

### A. The plugin, as documented

Add the plugin, generate keys, publish `latest.json`, call
`check()`/`downloadAndInstall()`.

Cheapest, cross-platform in one move, maintained upstream. Loses both
behaviours above: no codesign pinning, and a downgrade loop on dev
builds.

### B. Port `UpdateInstall.swift`

Keep the pinning and the describe defence exactly.

An in-place bundle swap is native work per platform, which means Rust
commands, which the ADR refused eight hours ago for a smaller reason. It
also means this project maintains its own updater on three platforms,
which is the largest single item in the retirement and the least
differentiated work in it.

### C. Plugin for transport, engine for judgement — RECOMMENDED

Split along the line the governing ADR already draws. The plugin does
what is mechanical: network, signature, download, swap. The engine does
what is a decision: whether this release is newer than the running build.

Concretely:

- **`src/update/compare.ts`**, new, pure, no network. Ports
  `isNewer`, `normalized`, the describe-suffix detection and the release
  selection. This is 59 of the 85 checks
  (`updater-version-compare` 17, `update-selection` 17,
  `update-decoding` 14, `update-error-descriptions` 11) and every one of
  them is pure logic that belongs in the engine by the ADR's own rule.
- **`desktop/ui/update-compare.js`**, GENERATED from it by a tool, with a
  test pinning the committed module to the generator's output, exactly as
  `notes.js` and `tests/desktop-notes.test.ts` already do. That is how
  engine logic reaches a window with no build step, and the pattern is
  proven here.
- **The window calls the plugin's `check()`**, then applies OUR
  comparator to `update.version` against `update.currentVersion`, and
  only offers the update if our comparator agrees. A dev build past the
  tag is therefore never offered a downgrade, because our rule overrules
  semver's.
- **The plugin installs.** The 26 installer checks are replaced in kind
  rather than ported, and the pinning is the accepted loss.

What C costs that A does not: one generator, one generated module, one
test. What C buys: the describe defence survives, 59 checks land as
ordinary `bun test` coverage in the engine, and the network stays out of
the engine entirely.

What C does NOT recover: codesign pinning at install time. No option
short of B recovers it, and B costs Rust commands on three platforms.

## The engine stays offline, and the README changes anyway

The plugin does its network in Rust, so `src/` gains no network code and
the promise that *"the conversion engine makes no network requests of any
kind"* stays literally true.

Two README sentences still go false and must change in the same commit:

- Line 239: *"The cross-platform window has fewer: no update check, no
  external links, and no send-to-kindle page."* All three clauses are
  wrong once this and piece B land.
- The five-touchpoint list for the Mac app becomes the shape the Tauri
  app has too, rather than a Swift-only paragraph.

The update check must be **off by default and asked once**, matching the
Swift app, whose preference is `updateOptIn` and which the README
describes as "off by default, and the first-launch page asks once". This
is a privacy promise the product has already made and the new app
inherits it.

## What the owner has to do, and it is twice

1. **Generate the key pair**, on his machine, and store the private half
   where the Apple certificate lives. Not me: losing it is unrecoverable
   and a private key should not pass through a session transcript.
2. **Add `TAURI_SIGNING_PRIVATE_KEY`** (and a password if he sets one) as
   repo secrets, then hand over the PUBLIC key, which is safe to share.

Everything else is mine: the plugin, the config, `latest.json` generation
in `release.yml`, a freshness check so the manifest cannot go stale the
way the Homebrew tap did, the comparator, the generator, the UI and the
tests.

## The one decision left open

**Is losing install-time codesign pinning acceptable?**

The honest framing: today an attacker needs this project's Apple
Developer ID certificate to push an update. Under A or C they need the
minisign private key. Both are secrets in the same GitHub account, so in
practice the blast radius is similar, and the artifact is still notarized
either way. But it is a weaker statement than the one the frozen app
makes, and `retired-coverage.md` said this behaviour must survive.

Recommendation: **accept it, and write it down** in
`docs/retired-coverage.md` as a change from `port` to `replaced` for
`self-update-installer`, with this paragraph as the reason. The
alternative buys a stronger guarantee for the cost of maintaining a
bespoke updater on three platforms, and this project has exactly one
person maintaining it.

## What this spec does not decide

The endpoint's shape beyond "a static `latest.json` on the release", the
UI of the update prompt, and whether Windows and Linux get the updater in
the same release as macOS. All are plan-level and none blocks the
decision above.
