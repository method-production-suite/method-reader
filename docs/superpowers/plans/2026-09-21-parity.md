# Plan: close the parity gap, in four pieces

Decision: [ADR 2026-09-21](../../adr/2026-09-21-doors-not-commands.md).
Evidence: [the parity audit](https://github.com/method-production-suite/method-reader/blob/7eb40e5/docs/parity-audit.md).
Blocks: v0.6.1 in [the handover plan](2026-09-20-swift-to-tauri-handover.md).

Piece-level, matching this repo's other plans. Each piece gets its own
bite-sized plan when it starts, because three of the four are well
understood and the first one is not yet.

## Order, and why it is this order

**A. The updater** is first because it is the only gap that cannot be
fixed after the handover. Everything else can be delivered by a later
update, provided the user can receive one. 85 of the 171 unreplaced
checks.

**B. The route model and the shims** is second because it is what an
upgraded user meets on day one, and because the interface-pass session's
piece 4 is blocked on it. 55 checks.

**C. The gear** is third: smaller, and its absence is a settings
annoyance rather than a missing route. No kit-check section of its own.

**D. The KFX install surface** is last only because it is nearly free and
can ride with anything. Zero new engine code.

v0.6.1 ships after A. B, C and D may land before or after it.

## Piece A: the updater

**BLOCKED ON A DESIGN DECISION, and this plan does not make it.** Write
`docs/superpowers/specs/<date>-updater-design.md` first. The question:

- **Tauri's updater plugin.** Cross-platform, maintained upstream. Wants
  a key pair (a new repo secret) and a published update manifest (a new
  release artifact, and a new thing that can go stale the way the
  Homebrew tap did). Its verification is its own signature scheme, NOT
  codesign requirement pinning.
- **A port of `UpdateInstall.swift`'s behaviour.** Keeps codesign
  pinning, which `docs/retired-coverage.md` says must survive "whatever
  shape" the updater takes, and keeps the downgrade defence that was
  "found the hard way once already". But an in-place bundle swap is
  native work per platform, and this project has exactly two Rust
  commands and a decision not to add a third.

Those pull in opposite directions and the tension is the real content of
the spec. Do not start coding until it is resolved.

What the spec must cover either way, from `docs/retired-coverage.md`:

| Behaviour | Checks | Why it cannot be dropped |
| --- | --- | --- |
| version comparison | 17 | carries a downgrade defence found the hard way |
| update selection | 17 | which release, which asset |
| update decoding | 14 | a malformed release must not crash the check |
| error descriptions | 11 | the difference between a message and "The operation couldn't be completed." |
| the installer | 26 | pinning and the in-place swap |

Two facts this plan can already state, because they are measured:

- The asset picker must be explicit about WHICH `.dmg`. GitHub returns
  release assets in NAME order, not upload order, which the old app's
  `assets.first(where: .hasSuffix(".dmg"))` gets away with only because
  the release will carry one DMG after v0.6.1.
- Whatever ships must be checkable by `tools/verify-signing.ts`, which
  already knows the pinned requirement and the notarization rules.

**Done when:** a Tauri build can find, verify and install a newer Tauri
build on macOS, and the five behaviours above have tests in `bun test`.

## Piece B: the route model and the shims

**Done 2026-09-23** on branch `parity-b-routes`:
[the design spec](../specs/2026-09-23-send-routes-design.md), [the engine
plan](2026-09-23-send-routes-engine.md) and [the window
plan](2026-09-23-send-routes-window.md). The window gained exactly one new
permission, `dialog:allow-save`; the owner decided the same day that the
ENGINE opens Apple Books, Amazon's Send to Kindle app and page, and Mail,
the same way it already runs Calibre, so those four routes cost the window
no permission of their own.

Engine side is mine; the drawing is the interface-pass session's piece 4.
They have already specified the contract they want, in decision 25 of
`docs/superpowers/specs/2026-09-20-desktop-ui-pass-design.md`:

> a route list from the engine (`id`, `title`, `detail`, `button`,
> `available`) and a "perform route X" call, because the ranking and the
> remembered choice are decisions, and decisions belong on your side of
> the line

That is the right split and this plan adopts it.

**B1. Port `ResultActions` to TypeScript.** `src/export/routes.ts`, new.
The catalog, the ranking, and the rule that **what you chose last time
beats any heuristic**. Unavailable routes stay in the list as dimmed rows
carrying their own fix, rather than disappearing. 45 checks
(`send-menu`).

Two states, not one, and the Swift app never had to express this: "plug
it in over USB" is a different unavailability from "not available on
Windows". Apple Books, the Send to Kindle app and Apple Mail are
macOS-only and this is three platforms now.

**B2. The remembered choice needs somewhere to live.** There is no
app-wide settings scope today (see piece C). Either B1 carries a minimal
one or it waits for C. Decide at the start of B, not halfway through.

**B3. Add one plugin, grant scoped permissions.**
`tauri-plugin-opener` is a NEW dependency: it is the only plugin that
reveals a file in Finder, where `tauri-plugin-shell`'s open would open the
containing folder without selecting the file. `dialog` is already a
dependency. Grants go in `desktop/src-tauri/capabilities/default.json`
with allow-lists, not blanket: the bug tracker and Amazon's pages for
`opener:allow-open-url`, the library for `opener:allow-open-path`.

`tests/desktop-shell.test.ts:366` asserts
`expect(cap.permissions).toEqual(['core:default'])`, so it WILL fail, and
that is the tripwire working: change it deliberately and rewrite its
comment to say the window now holds two doors and still no commands.
`desktop/README.md` says "the capability is still `core:default`" at line
131 and again at 158; both become false in the same commit. Its line 464
already anticipates this, calling out that some features "mean a new
Tauri plugin and a new capability grant".

**B4. The four routes.** Apple Books (hand a file to another app),
Send-to-Kindle (open a URL), email-to-Kindle (open a mail URL), and
save-a-copy (a SAVE dialog, which `pick_file` is not: it is an OPEN
dialog). 5 checks (`mail-and-books`) plus the save flow.

**B5. Feedback and Report a Bug.** 5 checks (`feedback-url`), ~20 lines
of URL building. The failure-screen variant carries the error's code and
message into the report and is the only path by which a refusal reaches a
bug report, so it is the one that matters.

**B6. Show in Finder**, in both places the Swift app has it: the reader
rail and the result screen.

**Done when:** the engine answers a route list, the window can perform
every route on macOS, and the platform-specific rows say which kind of
unavailable they are.

## Piece C: the gear

**Done 2026-09-23** on branch `parity-c-gear`:
[design](../specs/2026-09-23-app-settings-gear-design.md),
[engine plan](2026-09-23-app-settings-engine.md), [window
plan](2026-09-23-app-settings-window.md).

Three things, and Tauri has no app-wide settings scope at all.

- **Output folder**, with a picker and a Reset. Today the library is
  engine-owned and overridable only by `$SCREEPUB_LIBRARY`, so nobody can
  change where their books land without setting an environment variable.
- **Save as app defaults**, promoting one script's settings to app-wide.
- **Reset to Defaults.**

**Corrected while writing this plan.** I first wrote that
`resolveFormatOptions`'s `base` parameter was "already done and unused".
It is done and USED: `src/settings/sidecar.ts:55`, `src/cli-settings.ts:56`
and `src/cli.ts:590` all pass a second argument, so a sidecar already
merges over a fallback rather than over the shipped defaults. The
mechanism is not the gap.

The gap is that there is no app-wide settings STORE for the fallback to
come from. The engine can already layer; nothing writes the layer
underneath. That makes C smaller than it looks, and it makes B2's
question concrete: the remembered route choice wants the same store.

**Done when:** a user can change the library location and reset it from
the window, and app-wide defaults exist as a layer under the per-script
sidecar.

## Piece D: the KFX install surface

**Done 2026-09-23** on branch `parity-d-kfx-install`:
[spec](../specs/2026-09-23-kfx-install-surface-design.md),
[plan](2026-09-23-kfx-install-surface.md). The window also links to the
Calibre and Kindle Previewer download pages, which added three exact URLs
to the opener grant (approved by the owner the same day).

It was not "zero new engine code", as the order above guessed. The engine
gained two verbs (`kfx-status` and `kfx-install`, in `src/cli-kfx.ts`), a
checklist module (`src/export/kfx-setup.ts`, which the CLI prints and the
window draws, so the two cannot tell different stories), a plain offline
message in place of Python's own exception text, and a refusal to install
on a system Amazon makes no Kindle Previewer for.

`src/export/kfx.ts` already exports `installKfxPlugin`, fully implemented
and tested, with **zero callers outside its own file and tests**. The CLI
reads `kfxStatus` to decide what it can build and never offers to install.
Swift had an "Install plugin" button.

So this is not a port. It is a surface over a capability that already
exists, and it is the cheapest item in the whole audit.

**D1.** A CLI verb, so it is reachable without a window at all.
**D2.** A button on the Send surface when `kfxStatus` says the toolchain
is present but the plugin is not.

**Done when:** a user with Calibre and no KFX plugin can install it from
either the CLI or the window.

## What this plan does not do

It does not add Cancel. That was refused twice, most recently on
2026-09-21 after gate 2, and the shell staying at two commands is
load-bearing for it.

It does not delete `app/`. That is F3 and it stays blocked until A
through D are done and have been live through a release.

It does not touch the parser, the renderers or `format-defaults.json`.
